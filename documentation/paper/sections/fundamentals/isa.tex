\subsection{Instruction Set Architecture}

An \ac{isa} defines the shared behaviour of different implementations of said \ac{isa}. It is an abstract model that guarantees compatibility of software between computers of different implementation. This is called binary intercompatibility. It describes the supported set of instructions, their behaviour, as well as a memory model. The memory model describes the number and roles of all registers, as well as the behaviour of accessing memory and external interfaces. The latter part is also called the ``IO-Model'' of the \ac{isa}. An \ac{isa} may be designed to be extensible or closed for future modifications. 

\subsubsection{ISA vs. Implementation} \label{sec:isa_vs_implementation}

An \ac{isa} is an abstract model and does not specify \textit{how} it is to be implemented. When a \ac{cpu} implementing a specific \ac{isa} is designed, the designers are largely free to choose the exact implementation details, as long as the end product adheres to the rules laid out by the \ac{isa}. The distinction between an \ac{isa} and an implementation of said \ac{isa} is important; an \ac{isa} by itself cannot run code. There may be multiple implementations of one \ac{isa} using vastly different electrical or logical technologies. Due to the boolean logic transformation rules mentioned in \autoref{sec:logical_operators}, there is an infinite number of possible implementations, even when the same electrical components are used. Many \ac{isa} also leave room for interpretation or choice when it comes to electrotechnical details such as the voltage levels used, etc. An implementation of an \ac{isa} is also referred to as a microarchitecture. For example, the microarchitecture used by Intel for their flagship x86 \acp{cpu} is called the ``P6'' microarchitecture \cite{intel1997p6}.

\subsubsection{Memory Model} \label{sec:fundamentals_isa_memory_model}

A digital computer operates on data. The memory model of an \ac{isa} specifies how the data within the system is laid out. A memory in this context is any electrical circuit that stores some number of bits of information for later use. Registers store immediate data such as operands, results or variables and are intended to be read from and written to every cycle. They are addressed directly by the programmer through their individual names. Formally, this class of memory is called the internal storage of a \ac{cpu} \cite{bryant2015computer}. In addition to the set of registers, cache also falls into this category. However, since cache is implementation-dependent and may be implemented transparently to the programmer and to the \ac{isa}, it is not discussed here. Any useful program is larger than the amount of data that fits into the register set. Most programs also use far more memory to store temporary data such as variables. Therefore, in addition to the registers, other memories are available to the programmer. These memories are typically orders of magnitude slower to access when compared to the internal storage, especially the registers. However, in turn, they offer orders of magnitude more storage. In this context, all of these memories shall be referred to as ``main memories''. All memories that are physically implemented must be finite in size. Therefore, they are divided up into cells of usefully sized data.

A ``word'' is the smallest, atomic unit of data used by most operations of an \ac{isa}. It is specified as the number of bits that form one word, usually a power of two. For example, in a 32 bit architecture, the \texttt{ADD} operation will most likely operate on two 32 bit operands, ouputting another 32 bit result. The lowest level data storage units of the same \ac{isa} will most likely be designed to also contain 32 bit words to contain one operand or result each. Each word of $n$ bits can represent $2^n$ different values. This is typically a power of 2, since many of the circuits used to implement such systems naturally favor such sizes. This includes decoders, multiplexers and similar circuits. Early processors such as the Intel 4004 had a word size of 4 bits, meaning one word can represent 16 distinct values. Most modern systems have either 32 or 64 bit processors. However, even so, the venerable byte has remained as the smallest practical, individually addressable unit of bits, consisting of 8 bits each. It can therefore represent 256 distinct values. It has proven to be a good middle ground in terms of granularity and size. Most \ac{ram} and \ac{rom} components are byte-addressible, meaning they also handle data with a size of 8 bits each. If the programmer needs to process data that does not fit into a single word, multiple words can be used and processed in sequence to form arbitrarily large data. 

Similarly, multiple registers can be concatenated to hold a larger piece of data. For example, \ac{mips} uses two dedicated 32 bit registers ``HI'' and ``LO'' to store results of multiplication or division, since these can easily overflow a single 32 bit register when doing an operation with 32 bit operands \cite{mips1995}. Similarly, throughout the evolution of the x86 \ac{isa}, the initial 8 bit registers were first expanded to 16, then to 32, and most recently to 64 bit registers. To retain backwards compatibility, the smaller sections remain accessible to the programmer.

\autoref{fig:x86_register_sizes} shows the composition of a single general purpose register in the x86 architecture. The Intel 8086 was the first processor to implement the x86 \ac{isa}. It featured 8 general purpose 8 bit registers, which could be accessed in pairs of two to form 4 16 bit registers \cite[p. 1-6]{intelASM86Manual1983}. For example, the \texttt{AH} and \texttt{AL} registers can be accessed by some instructions as the 16 bit register \texttt{AX}. This pattern was extended to form 32 and eventually 64 bit registers. Using multiple registers in combination to form a single larger memory can be used by an \ac{isa} to index into larger memories than would otherwise be possible. It is also common practice for an \ac{isa} to feature registers of different sizes, including ones larger than the native word size. Again, this way, larger memories can be indexed, which can be used to increase the maximum size and complexity of programs.

Depending on the way the memory can be accessed by the programmer, an \ac{isa} falls into one of three proven memory models:

\begin{itemize}
    \item Von Neumann
    \item Harvard
    \item Modified Harvard
\end{itemize}

In a machine obeying the Von Neumann memory model, there is only one global memory space, which contains both data and program instructions. In a harvard architecture, these memories have a separate address space. A modified harvard architecture is functionally the same as a regular harvard one, but the software can access the instruction memory as if it was data, while still being stored in a separate memory. This is the memory model used by many modern \ac{isa}. Having two separate memories for storing data and program instructions has the main benefit of allowing different word and address sizes.

\subsubsection{Execution Model} \label{sec:fundamentals_isa_execution_model}

The stack based model uses a single working memory, which is organised by the \ac{lifo} principle. The operands of an operation are always the elements at a specified offset from the stack top. For example, an addition may pop the top two elements off the top of the stack and push the result back ontop. This method has the advantage of not having to specify operand locations in the instruction, allowing for more compact code. However, it lacks the ability to randomly access memory and frequent stack operations can be slow. 

The accumulator-based execution model has a fixed number of registers, one of which is the designated accumulator register. All operations that output a value will store this result in the accumulator register. The accumulator register is also always one of the operands to an operation. The other operand, if required, is read either from memory or from another register, which can either also be fixed or freely chosen by the programmer, depending on the instruction encoding scheme. This execution model is easy to implement and the instructions are also smaller compared to fully addressable operand/destination registers. It is often used in early \ac{cpu} such as the Intel 8008 and 6502 \cite{schlyter200513}. However, its performance is limited by the bottleneck of the accumulator register. it also requires frequent transfers between memory and registers or between registers to save intermediary results, which would otherwise be overwritten by another operation.

The register based execution model provides a fixed set of registers. This model is subdivided further into the ``Register-Register'' and ``Memory-Register'' models. \autoref{fig:register_architecture} shows the former, which is also known as a ``Load-Store architecture'', since the only way of transferring data between registers and memory is via the dedicated load and store operations. All operands and result destinations of an arithmetic operation are registers. The ``Memory-Register'' model allows operations to be read from memory instead. Due to the bottleneck in speed of modern memories, many modern register based architectures are of the Load-Store variant. The register based execution model is highly flexible and well understood. Operands and intermediary results can be reused efficiently and compilers can deterministically optimize register allocation, allowing for higher performance.

\subsubsection{Addressing modes}

There are many different modes of addressing memories. An addressing mode specifies which memory is accessed, and how the address for that memory is calculated. \autoref{fig:addressing_modes} shows a hierarchical overview of types of modes of addressing. The complexity and number of arithmetic operations required for each mode increase with column, starting at the left. Within each column, complexity increases from top to bottom.

    \centering
    \includegraphics[width=0.7\textwidth]{images/drawio/addressing_modes_general.png}  % Replace with your image file

Again, the complexity increases starting from the left. The more complex an addressing mode is, the more additional hardware is required. For the given modes, the most complex one is referred to as ``Base + Index + Scale + Displacement''. In this mode, the resulting memory address is calculated like so:

$$ \text{Base} + \text{Index} * \text{Scale} + \text{Displacement} $$

This requires additional hardware for performing the additions and multiplication. Note that the ``Scale'' is restricted to 1, 2, 4 or 8 and can therefore be implemented by shifting the index to the left by 1, 2, 3 or 4 bits. In most modern, and some older architectures, the addressing modes can be quite numerous and complex. For example, the Intel 6502 has 13 different addressing modes \cite[13.2.1]{schlyter200513}. However, an \ac{isa} need not implement a large number of addressing modes in order to be useful. For example, the Intel 8008 \ac{cpu} only has 3 addressing modes (Register, Register Indirect and Immediate) \cite{cpu-world8008}.


\subsubsection{Opcodes}

Every instruction is identified by its unique ``Opcode'', which is a discrete number. Based on this number, the processor must infer the number and layout of operands and set up the internal state for execution of the given instruction. The number of bits available for encoding the opcodes determines the maximum number of instructions supported by an \ac{isa}. Not all opcodes within this available range must be assigned. Depending on the design philosophy, unassigned opcodes may be equivalent to NOPs or cause undefined behavior. In some \acp{isa}, the number of bits per opcode is variable. For example, in the widely used x86 \ac{isa}, the opcode can be between 8 and 24 bits \cite{mahoney2021enumerating}. More frequently used operations are assigned a shorter opcode to increase code density.

\subsubsection{RISC vs. CISC}

Early microprocessors had - by necessity - simple instructions. There were typically also fewer instructions compared to modern systems. This was dictated by the technology at the time. More functionality requires more transistors, which require space on the die, as well as more capabilities for shedding heat. With the shrinking sizes of transistors, more complex instructions became feasible. As with the instructions, the complexity of other systems of a \ac{cpu} grew as well. For example, the Intel 8008 processor released in 1972 \cite{intel4004history} had only 48 instructions \cite{cpu-world8008}, whereas a modern x86 implementation supporting all extensions has $\approx 1795$ instructions \cite[Chapter 7]{heule2016stratified}. Depending on the complexity and number of instructions, an architecture is classified as either \ac{risc} or \ac{cisc}. There is no exact definition of either of these types. This distinction gives an indication of the design goals of an architecture.

\subsubsection{Types of Instruction}

Instructions can be divided up into different types based on their effects. There are instructions that perform some calculation and store the result in a target memory location. These instructions will be referred to as ``arithemtic instructions''. There are also instructions that do not calculate anything but simply move data between memories. Most \ac{risc} architectures follow the ``Load-Store'' paradigm. This paradigm says that only a select few instructions interact with main memory, whereas the rest of the instructions, including all arithmetic ones, interact only with immediate data and registers. These instructions will be referred to as ``transfer instructions''. Another important class of instruction is the ``control flow instruction''. As the name suggests, this type of instruction usually does not compute anything either, but is responsible for the decision making process within the \ac{cpu}. Upon executing such an instruction, the program counter, instead of being incremented, is overwritten with a value from a memory. This is called branching. There are unconditional and conditional branches, which only overwrite the program counter if some predicate is met. This predicate is typically dictated by a flag stemming from the result of the last arithmetic instruction. Branching is required for implementing function calls and general conditional execution, i.e ``Do X if Y, otherwise do Z''.

\subsubsection{Instruction Encoding}

In order for a processor to understand each instruction, it must be laid out in a predictable, well defined manner. This is called the instruction encoding format. This encoding must include all information required for performing a desired operation. The encoding must include the opcode, all operands and any additional settings required for executing an operation. Since different operations require a different number and type of operand, it can be useful to define a variable length encoding scheme to save memory and increase code density. On the other hand, variable length encodings require additional logic to determine the length from a given opcode and fetch the required number of bytes from memory. This introduces complexity in an implementation, as well as increasing the number of logic gates required. Typically, this also causes the fetch phase to take more than a single clock cycle. For these reasons, many \ac{risc} architectures use a fixed length encoding. Since different types of instructions require different combinations of options and operands, \acp{isa} may define multiple distinct encoding schemes. The instruction decoder can then choose the corresponding format for each opcode.

\subsubsection{Microcode}

With increasing complexity of individual instructions, more and more complex hardware is required to execute them. To retain a manageable level of complexity, complex operations can be split further into suboperations. These suboperations or microoperations form the instruction set that is directly executable on any given implementation or microarchitecture. The set of all supported microoperations is called microcode of an implementation. Any given instruction on the \ac{isa} level can then be implemented by one or more of these microoperations. Since programmers write their software for an \ac{isa} and not for a microarchitecture, this must be implemented in a way that is transparent to the programmer.

Depending on the level of abstraction that this microcode provides, the microcode is classified as either ``horizontal'' or ``vertical''. Horizontal microcode provides less of an abstraction over the hardware than the vertical counterpart. In microarchitectures using horizontal microcode, each microoperation is a direct binary representation of control signals. When the microoperation is executed, the control signals are applied to the relevant multiplexers and switches within the \ac{cpu}. In vertical microcode, each microoperation has a distinct opcode, similar to the \ac{isa}-level opcodes. The opcode serves as an identifier instead of a set of control signals. An additional hardware unit the decodes and interprets each microoperation. This approach resembles its own \ac{risc} computer that then implements another, possibly even \ac{cisc} \ac{isa}.

In horizontal microcode, each \ac{isa} operation may correspond to one or more microcode control words. During each clock cycle, one control word is executed. Therefore, executing an instruction with $n$ control words takes $n$ clock cycles. If a microarchitecture consists only of instructions where $n = 1$, it is called a single cycle processor. Otherwise, it is considered a multicycle processor. All control words must be the same size, therefore every instruction must provide a value for every control signal. Many instructions use only a small portion of the available hardware units, therefore a lot of the control word table is used for instructing hardware to remain inert.
